# Debug Tools 三端接入指南

适用远程预发布 `0.2.0-rc.1`。Maven 真远程消费已通过，OHPM 审核期间使用同版 Release HAR 并校验 SHA，见 [发布记录](../README.md#020-rc1-发布与远程验收)。`0.1.3` 已发布的 Android/iOS API 继续保留；升级后不需要更换现有 ViewModel 所有权。

## 共用状态与平台边界

Android/iOS 使用 `BugReportViewModel(repository, hostDataSource, formatMessage)`；内部委托 `BugReportController`。OHOS 使用 `BugReportController(pageScope, repository, hostDataSource, formatMessage)`，所有操作和 scope 属于同一个 Kuikly Page Context。不要把 Android 的 `Dispatchers.Main` 当作 Kuikly Context。

宿主观察 `state` 并提供表单、导航、准入和资源文案。`BugReportHostDataSource` 只提供当前上下文与证据，组件不感知品牌、用户业务或 diagnostics 实现。生命周期结束前，在所属 UI/Page scope 等待 `flushDraft()`；不启动脱离页面的常驻协程来保存。

`ZentaoBugClient` 使用宿主提供的专用 TLS HttpClient Engine。目标 HTTPS 地址、产品、分支和 openedBuild 必须显式配置；未开通时使用 `BugReportTarget.Unavailable`。组件关闭自己的协议客户端，宿主继续拥有传入 Engine 的生命周期。账号密码不落盘。

## Store 与升级

Android：`AndroidBugReportStore` 使用 Keystore AES/GCM Token、私有 SharedPreferences；草稿和 pending 的写入在 IO 调度器同步 commit，成功返回代表本机记录提交完成。

iOS：`IosBugReportStore` 保留原 Keychain service/account 与 NSUserDefaults 历史/开关键；草稿和 pending 使用 Application Support 私有目录原子文件并排除备份。

升级继续注入原 namespace、keyAlias/service/account、tokenKey、historyKey 和 shakeEnabledKey，不把 Token 复制到新空间。新增 draftKey/pendingKey 可使用默认值；必须按品牌、产品、账号隔离，不允许两个独立 Repository 同时管理同一队列命名空间。退出/切换账号时先撤销旧页面与 Repository，再使用对应空间。

现有自定义 `BugReportStore` 保持兼容，只有实现 `BugReportWorkspaceStore` 才提供持久草稿、队列和附件恢复。组件不会假装旧 Store 已保存 workspace。`clearCredentials()` 仅清 Token，保留草稿、历史与设置。

## 鸿蒙原生与 Kuikly 注册

Maven 候选 `debug-tools` 提供核心 OHOS KLIB，`debug-tools-kuikly` 提供桥；原生配套 HAR 为 `@gycrosskit/debug-tools-native:0.2.0-rc.1`。三个版本保持一致。

ArkTS renderer 注册 `GycDebugToolsModule.MODULE_NAME` 对应的 `GycDebugToolsModule`，Kuikly Page 注册 `DebugToolsModule`；从 Page 获取该 Module，先完成配置，再创建 Repository/Controller：

```kotlin
// 此代码在所属 Page scope 执行；Module 的注册/获取沿用宿主现有 Kuikly 接入。
module.configure(namespace = "brand_debug", keyAlias = "brand_zentao_token")
val repository = BugReportRepository(ZentaoBugClient(engineClient, target), module)
val controller = BugReportController(pageScope, repository, hostDataSource)
```

HUKS 使用持久 AES-256-GCM 密钥、每次写入独立随机 nonce 和 namespace AAD；偏好中只保存 nonce/密文。失败会报告错误，不退回明文，也不因暂时系统错误删除密钥。页取消/销毁撤销原生请求所有权，已开始或已完成的提交不能视为回滚。

宿主 module.json5 声明 `ohos.permission.ACCELEROMETER`。真实注册成功才返回 STARTED：

```kotlin
when (module.startShake()) {
    ShakeStartResult.STARTED -> Unit
    ShakeStartResult.SENSOR_UNAVAILABLE -> showSensorUnavailable()
    ShakeStartResult.REGISTRATION_FAILED -> showSensorRegistrationFailed()
    ShakeStartResult.CLOSED -> Unit
}
// 已有 Page scope 收集 module.shakes，宿主决定是否打开表单。
// 前后台/准入变化时 suspend stopShake()；页销毁在相同 Context 调用 dispose()。
```

Android/iOS 原 ShakeDetector 的 start/stop/close 仍在主线程调用；OHOS 桥用 suspend 等待原生回执，不将排队视为成功。三端保留 2.7g、1200ms 冷却，事件无 replay；停用不重置冷却。OHOS 传感器使用 m/s²→g 转换和单调 timestamp。

原生工程 compatible/target 声明 API22，使用的接口最低要求 API12；当前实跑编译 SDK 为 API26，不能据此声称独立 API22 SDK 或真机行为已经验收。

## 草稿与手动恢复

编辑自动保存用户输入；`saveDraft()` 显式保存，`queueDraft()` 放入待提交列表，`submitPending(id)` 由用户点击触发。启动/联网/授权仅恢复状态，不触发远端创建。队列最多 10 条未完成记录，已完成回执保留最近 20 条用于防止同一草稿重复提交。

`BugReportDraft.reportId` 是稳定身份。编辑时使用 `copy` 保留它；新建报告才生成新 Draft。不能因为上次结果未知而人为换 reportId 重试。待提交记录还绑定原 apiBase/product/branch/openedBuild；换目标时会拒绝发送。

| 状态 | 操作 |
| --- | --- |
| READY | 用户点击 submitPending，先本机保存 UNKNOWN，再创建 Bug |
| UNKNOWN | 先核查禅道；已创建调用 confirmCreated(id, bugId)，确认未创建才传 confirmedNotCreated=true 重试 |
| CREATED | 保留 Bug ID/链接，不再创建；剩余附件通过 retryAttachments 补传 |

网络超时、取消、缺失 ACK 不证明服务器未创建。已知 Bug ID 后保存历史/附件失败仍显示创建成功；`workspaceSaved=false` 表示本机恢复记录不完整，用户应先核查禅道。取消不会自动回滚远端动作。

待提交只保存用户表单与附件标识，不保存 Token、密码、附件内容或自动日志。手动提交时重新取得当前上下文和证据；宿主须确认它们适用于该草稿，不把旧问题的设备现场误写成当前现场。

## 附件

宿主核验支持 REST v2 文件上传的禅道版本后，将 `BugReportTarget.Configured.attachmentsEnabled=true` 并向 Repository 注入 `loadAttachment`。开源禅道 22.0 起有该接口，实际以宿主部署契约为准，见 [官方 files 文档](https://www.zentao.net/book/api/post-files-2325.html)。

```kotlin
val repository = BugReportRepository(
    ZentaoBugClient(engineClient, target),
    store,
    loadAttachment = { attachment -> hostFiles.read(attachment.id) },
)
controller.updateAttachments(listOf(BugReportAttachment(
    id = stableFileId, fileName = "capture.png", contentType = "image/png", size = fileSize,
)))
```

最多 3 个附件、每个 4MiB。宿主负责选择、截图、权限与稳定私有文件副本；引用在应用重启后仍须可读取。文件名/MIME/大小在信任边界校验，实际读取字节数必须等于声明。组件不读取任意路径、不自动采集、不持久化附件字节。

创建得到正 Bug ID 后，客户端 POST `/v2/files`，Token Header、multipart file/objectType=bug/objectID。每个已确认 File ID 落盘后不再上传；未知附件先核查：已上传调用 `confirmAttachmentUploaded(id, attachmentId, fileId)`，确认未上传才将对应 id 放入 `retryAttachments` 的 `confirmedNotUploaded`。

附件授权/权限错误通过 `state.attachmentNotice` 保留 typed cause，同时 `submittedUrl`/Bug ID 仍代表创建成功。宿主应显示已创建和需要重新授权/补传两个信息，不显示整个 Bug 创建失败。

## 本地化与准入

`BugReportNotice.code` 用于宿主资源映射；内置 `notice.text(CHINESE/ENGLISH)`，Controller/兼容 ViewModel 注入 formatter，`ZentaoBugClient` 的 reportLanguage 控制 Bug 正文标签。业务表单、导航和宿主资源仍由宿主本地化。

`BugEvidenceFormatter` 仅限长，不能替代脱敏。日志/上下文是否进入 Bug 正文由宿主准入决定。开发/QA 才启用调试入口；组件不接管环境切换、SDK 调试按钮、分享或诊断上传。
